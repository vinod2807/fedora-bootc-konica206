# Konica bizhub 206 print-path comparison

Reference notes recorded 2026-11-17 on a Fedora 45 bootc host running
`ghcr.io/vinod2807/fedora-bootc-konica206:latest` (systemd 262) with the
bizhub 206 attached over USB (`132b:232b`). No bootc image content was changed
by this comparison; it documents runtime behaviour only.

Related reading: [PRINTER.md](PRINTER.md),
[DUPLEX-BACKSIDE.md](DUPLEX-BACKSIDE.md).

## 1. The three paths and where their source lives

| Path / CUPS queues | Source repo | Role |
|---|---|---|
| Native PAPPL — `konica206`, `konica206-classic` | [vinod2807/fedora-bootc-konica206](https://github.com/vinod2807/fedora-bootc-konica206) | This image: builds the app/renderer into `/usr`, ships the shim PPDs with 12 pt margins, and the service units |
| Legacy app — `konica206uri`, `konica206uri-ppd` | [vinod2807/konica-retrofit](https://github.com/vinod2807/konica-retrofit) | pappl-retrofit Legacy Printer Application setup and backed-up PPD variants |
| Alpine + systemd-nspawn — `konica206-nspawn` | [vinod2807/konica206-alpine-nspawn](https://github.com/vinod2807/konica206-alpine-nspawn) | Host-managed Alpine rootfs, PAPPL app as container PID 1 on `127.0.0.1:8002` |

Shared code dependencies for all three:

- [konica206-native-alpine](https://github.com/vinod2807/konica206-native-alpine) — the PAPPL application (itself derived from
  [konica206-native](https://github.com/vinod2807/konica206-native)).
- [konica-native-musl](https://github.com/vinod2807/konica-native-musl) — the C11 device-stream renderer, built for glibc in this
  image and for musl in the nspawn rootfs.

A fourth, inactive option is [konica206-via-podman](https://github.com/vinod2807/konica206-via-podman)
(Debian 12 CUPS container, `Konica_Via_Podman`). Its host PPD also declares ~12 pt margins.

## 2. Why the printed margins differ

Measured `*ImageableArea` for A4 in the installed queue PPDs:

| Queue | `*ImageableArea A4` | `*cupsBackSide` |
|---|---|---|
| `konica206` | `12 12 583.28 829.89` | `Rotated` |
| `konica206uri` | `12 12 583.28 829.89` | `Rotated` |
| `konica206uri-ppd` | `12 12 583.28 829.89` | `Rotated` |
| `konica206-classic` | `12 12 583.28 829.89` | `Rotated` |
| `konica206-nspawn` | `0 0 595.27559 841.88976` | `Normal` |

The four host queues inherit the image's PPD family: `ppd/konica206.ppd`,
`ppd/konica206-classic.ppd`, and the derived `konica206-app.ppd` with the PDF
duplex shim. Their comments state the design intent: the bizhub 206 is assumed
to have ~4.2 mm hardware margins, so the 12 pt inset is deliberate and the
zero-margin `.Borderless` names generated by CUPS are rejected.

`konica206-nspawn` instead uses the unmodified driverless PPD shipped by
`konica206-native-alpine`, which declares full-bleed geometry.

Empirical check with two generated 2-page A4 test PDFs — an 8 mm border sheet
and a 2 mm border sheet, both with FRONT/BACK and near-edge TOP/BOTTOM markers:

- `konica206` and `konica206uri` print the borders inset by roughly 4.2 mm
  relative to the designed positions, and match each other.
- `konica206-nspawn` prints them at the designed positions, noticeably closer
  to the paper edge.

So the margin difference is a **queue PPD geometry choice**, not a difference
between the renderer builds or the PAPPL versions.

Note the tension with the guidance in [PRINTER.md](PRINTER.md) for the retrofit
full-bleed PPD: "*ImageableArea must stay equal to \*PaperDimension for every
size: an inset area makes the encoder's raster smaller than the sheet the
device declares and ghosting appears." The host queue PPDs deliberately use an
inset, so that trade-off should be re-checked on paper if the margins are ever
changed.

## 3. Resource usage measured on this host

| Component | Idle | Peak during a short-edge duplex A4 PDF job |
|---|---|---|
| Native PAPPL app (`konica206-native.service`) | 5.7 MiB cgroup (13.8 MB RSS) | **12.3 MiB** |
| `cups.service` (conversion for the native path) | ~26 MiB | **49.8 MiB** |
| Native path combined | ~32 MiB | **~62 MiB** |
| Alpine/nspawn container | 72 MiB cgroup (mostly reclaimable page cache; ~11 MB process PSS) | **209 MiB** |

The native path is ~3x lighter at peak. Much of the gap is *where rendering
happens*: with a CUPS proxy queue, CUPS performs the PDF/raster conversion in
its own cgroup; in the nspawn app, Ghostscript runs inside the container, so
that memory lands in the nspawn cgroup. `memory.peak` could not be reset on
this kernel, so the job-specific peaks above were obtained by sampling
`memory.current` every 0.2 s during the job.

## 4. USB sharing model

USB interface 1 is opened **per job**, not held for the lifetime of a service.
With all three PAPPL services running, no process held the device node open at
idle. Two concurrent jobs from different paths would collide on
`libusb_claim_interface(1)`; the loser aborts and its queue pauses until the
device is available again. There is no need to stop one path just to keep
another running.

## 5. Reproducing the margin check

Test documents used (generated locally, A4, 2 pages):

- `~/Documents/narrow-margin-test.pdf` — outer border 8 mm from each edge,
  inner guide 12 mm.
- `~/Documents/edge-margin-test-2mm.pdf` — outer border 2 mm, inner guide 4 mm,
  edge labels 1.2 mm from the paper edge.

Submit with, for example:

```sh
lp -d konica206 -o PageSize=A4 -o Duplex=DuplexTumble ~/Documents/edge-margin-test-2mm.pdf
lp -d konica206-nspawn -o PageSize=A4 -o Duplex=DuplexTumble ~/Documents/edge-margin-test-2mm.pdf
```

Check that all borders are visible and evenly spaced, the TOP marker is at the
top on both sides, and the FRONT/BACK pages pair correctly on one sheet.

## 6. Maintenance implications

- Change host-queue geometry in the **source** PPDs in this repo (`ppd/`), not
  in `/etc/cups/ppd`, which CUPS regenerates. Remember the duplex shim variant
  used by the legacy proxy queues.
- The nspawn PPD and its service model live in `konica206-alpine-nspawn`; its
  USB passthrough needs both `DeviceAllow=char-usb_device rwm` in the service
  unit and `--setenv=` for app environment variables (service `Environment=`
  does not reach PID 1 inside the container). See that repo's
  `docs/architecture.md` and `docs/troubleshooting.md`.
- This file is observational reference material, not an acceptance gate.
  Physical print tests remain the authority.
